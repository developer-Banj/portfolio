Self-Directed API Security Labs

Breaking two deliberately-vulnerable APIs, start to finish

A practical write-up of two assessments I ran for myself against Capital (c{api}tal) and VAPI — two apps built specifically to be broken, so I could test the OWASP API Security Top 10 end to end without touching anything real.

OWASP API Top 10 Burp Suite Postman

Reading about BOLA or mass assignment is one thing. Finding them yourself, in a live request, with your own hands on Burp Repeater, is a completely different kind of learning — the kind that sticks. So alongside my work on crAPI, I picked two more intentionally-vulnerable targets built for exactly this, and worked through each one methodically against the OWASP API Security Top 10.

Capital — c{api}tal

Capital (built by Checkmarx as a CTF for Black Hat Europe and DEF CON) is dressed up as an article-and-membership site, but underneath it's a deliberate tour of almost the entire OWASP API Top 10 in one application. I went through it endpoint by endpoint, mapping what the front end exposed against what the API itself would actually accept.

Broken function-level authorization

An admin-only endpoint that didn't actually check whether the caller was an admin — a regular authenticated session was enough to reach it.

Broken object-level authorization (BOLA)

Swapping an ID in a comment-delete request let me remove a comment that belonged to a different account entirely.

Broken authentication

Profile content leaked enough about a user that their password became guessable without touching the login endpoint's rate limiting at all.

Excessive data exposure

The membership flow handled card data in the API responses more loosely than the UI ever let on.

Mass assignment

A field that should never have been client-writable — an "admin" flag — accepted a value straight from my request body.

Security misconfiguration

An exposed internal database, reachable directly, with no business reason to be internet-facing at all.

VAPI (Vulnerable Adversely Programmed Interface)

VAPI is a self-hosted Laravel/MySQL API built purely for this kind of training, shipped with its own Postman collection to get you authenticated fast so the actual testing can start sooner. I spun it up locally rather than against anything public, and used it to drill the categories Capital didn't cover as deeply:

Injection

Parameters that reached the database layer without the sanitization the application assumed was happening upstream.

Insecure direct object reference

Resource IDs that were sequential and unchecked — predictable enough to enumerate another user's data by just incrementing a number.

CORS misconfiguration

A response header permissive enough that a browser from an untrusted origin could still read the API's responses.

What carried over

The value of running both wasn't the individual bugs — those are deliberate, and documented, and meant to be found. It was building a repeatable process I still use: map the real API surface first (not just what the UI calls), test authorization on every single object and function independently rather than assuming a working login means a working permission model, and always look at what a request would accept, not just what the front end sends.

Note: I also ran an early assessment against TPay, a real internal payment platform at a company I interned with — that one isn't written up here, since it wasn't a public training lab and the details aren't mine to publish.
